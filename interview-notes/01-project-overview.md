# 功能 01：系统闭环与工程化亮点（面试讲法）

## 1) 这个功能解决了什么问题

法律文书生成的难点不是“能不能调用大模型”，而是把 AI 输出稳定接入业务流程。这个项目把流程打通为：上传案情描述 -> AI 结构化抽取 -> 实时流式回填表单 -> 一键导出 Word。

面试里可以强调：我做的是“可交付的 AI 应用工程”，不是单点 Demo。

## 2) 你在项目里的可讲贡献

- 设计并落地端到端链路：输入文本、AI 解析、前端回填、文档导出。
- 把 AI 能力工程化：字段白名单、重试机制、超时控制、取消机制、链路追踪。
- 把文档生成做成前端可用能力：Web Worker + docx XML 处理，保证 UI 不阻塞。
- 完成可部署方案：Docker Compose 三容器（MySQL、Node、Nginx）。

## 3) 30 秒自我讲述（可直接背）

我做了一个 AI 法律文书生成系统，重点是把模型能力稳定接入真实业务流程。用户上传案情后，后端用 Function Calling 做结构化抽取，并通过 SSE 实时把字段回传到前端。前端逐字段回填表单，用户可以随时取消。最后通过浏览器端 docx XML 引擎生成 Word，复杂表格和多人信息都能正确填充。整个系统有鉴权、限流、超时和可部署方案，不是单纯的聊天应用。

## 4) 技术亮点拆解（面试官追问用）

### 4.1 AI 工程化而不是裸调用

- 为什么重要：大模型输出不稳定，直接用会导致字段缺失或格式错乱。
- 怎么做：Function Calling + 字段白名单校验 + 最多 2 次重试 + requestId 追踪。
- 结果：输出更可控，问题可定位，线上可运维。

### 4.2 流式回填提升感知性能

- 为什么重要：一次性返回会让用户长时间无反馈。
- 怎么做：SSE 增量返回，前端收到一个字段就填一个字段。
- 结果：用户等待焦虑降低，可见“系统正在工作”。

### 4.3 前端文档引擎降低后端压力

- 为什么重要：文档填充和压缩是 CPU 密集任务。
- 怎么做：Web Worker 承担 docx 解析/填充/打包，主线程只负责交互。
- 结果：页面不卡顿，体验更稳定。

### 4.4 交付能力体现工程完整度

- 为什么重要：面试官关心“能否落地上线”。
- 怎么做：Docker Compose 编排 + Nginx 代理 + 环境变量管理。
- 结果：本地和部署环境行为一致，上手和迁移成本低。

## 5) 高频追问与回答模板

### Q1：这个项目最难的点是什么？

最难的不是调 API，而是把不稳定的模型输出变成稳定的业务字段。我通过白名单校验、重试、超时和可取消机制，把模型输出接到了可观测、可回溯、可维护的流程里。

### Q2：为什么用 SSE，不用轮询？

轮询会增加请求开销且实时性差。这个场景是“服务端不断产出增量字段”，SSE 更贴合单向实时推送，前端实现也更轻量。

### Q3：为什么要做 Web Worker？

docx 处理会占用主线程，直接在 UI 线程做会卡顿。把解析和打包放进 Worker 后，主线程只做渲染和交互，体验明显更稳定。
